## 一、拆分单据类型与产品来源

当前页面把“需求单/选产品库”和“报价单/手填产品”绑定在一起，需要拆成两个独立维度：

1. 单据类型：
   - `demand`：需求单
   - `quote`：报价单
2. 产品来源：
   - `existing`：从产品库选择
   - `candidate`：手填新产品需求

允许组合：

- 需求单 + 产品库产品：允许。
- 需求单 + 手填新产品：允许。
- 报价单 + 产品库产品：允许。
- 报价单 + 手填新产品：禁止，前端不提供入口，API 也必须拒绝。

新建页先选择“需求单/报价单”；需求单再选择“产品库产品/手填新产品”，报价单固定显示产品库选择器。编辑草稿时必须正确恢复原单据类型和产品来源。

历史单据保持可查看；历史手填报价单不强制迁移，但新建或重新编辑时必须遵守新规则。

## 二、路径 A：需求单 + 产品库产品

流程：

`需求单草稿 → 提交需求单 → 待老板审批 → 老板审批通过 → 可转销售单`

规则：

- 使用产品库已有销售价或按数量匹配的阶梯售价。
- 老板只审批需求单是否通过，不填写、不修改“老板确认售价”。
- 未经老板审批不得转销售单。
- 老板拒绝时保留审批记录和原因，不得转销售单；如项目已有退回草稿机制，沿用现有机制，不额外扩展新流程。
- 需求单审批状态与报价单的“老板确认售价”状态必须区分，不能共用一个含义模糊的状态。

## 三、路径 B：需求单 + 手填新产品

流程：

`需求单草稿 → 提交需求单 → 自动生成询价单 → 采购询价/多供应商比价 → 老板选择最终供应商并确认最终售价 → 创建或关联报价候选产品 → 转为报价单 → 进入销售记录客户反馈环节`

规则：

- 手填新产品需求提交后不能直接转销售单。
- 提交后自动生成询价单，沿用现有询价、比价、老板确认权限和页面。
- 老板确认时仍需选择最终供应商并填写最终销售价格。
- 老板确认完成后，不直接转销售单，而是生成/更新报价单。
- 报价单必须关联产品库产品，因此此时需要创建或复用产品阶段为 `quote_candidate` 的“报价候选产品”，并把报价明细关联到该产品 ID。
- 创建候选产品时复用现有产品编码规则和产品服务，避免重复 SKU、重复候选产品和绕过审计日志。
- 候选产品使用现有 `productStage`：
  - `quote_candidate`：报价候选产品
  - `formal`：正式产品
- `active/inactive/deleted` 是产品启用状态，不能代替产品阶段。
- 客户无后续时，产品继续保持 `quote_candidate`。
- 客户反馈价格有问题并重新询价时，复用同一候选产品和同一报价业务链。
- 客户接受报价并转销售单时，在产品资料满足现有正式产品校验规则后，调用/复用现有转正式能力，把候选产品转为 `formal`。所需销售编码按独立的销售编码规则自动生成，不得制造无法转正式的候选数据。

### 销售编码规则

- 销售编码属于产品库产品主数据，与采购编码分别配置、分别生成。
- 销售编码规则复用现有采购编码规则中心的组合段、排序、预览、校验和流水号能力，但使用独立配置与独立流水。
- 销售编码支持：固定前缀、产品分类编码、年、月、流水号。
- 销售编码不提供供应商编码段，避免向销售角色或客户侧编码泄露供应商信息。
- 候选产品可暂时没有销售编码；候选产品成功随销售单转为 `formal` 时，按当时启用的销售编码规则自动生成。
- 已有销售编码不重算；历史产品不批量回写；自动生成必须保证唯一并写入产品审计日志。
- 管理员可在产品编码规则中心分别查看、预览和配置采购编码规则、销售编码规则。

## 四、路径 C：报价单 + 产品库产品

流程：

`报价单草稿 → 提交报价单 → 待老板确认售价 → 老板确认最终售价 → 进入销售记录客户反馈环节`

规则：

- 报价单只能选择产品库中的有效产品。
- 首次提交不再自动生成采购询价单。
- 老板需要确认最终售价，但不需要首次采购询价。
- 老板未确认售价前，不能进入客户确认，也不能转销售单。

## 五、报价单客户反馈闭环

系统是内部系统，不提供客户登录或客户操作入口。客户确认结果由销售角色在报价详情页记录。

允许操作角色：销售、销售主管。老板和管理员可以查看结果；是否保留管理员代操作能力应沿用项目现有权限风格，不新增绕过权限的接口。

老板确认售价后的报价单进入“待客户反馈”，销售可记录三种结果：

1. 客户接受价格
   - 记录确认人、确认时间和备注。
   - 报价单变为“客户已确认”。
   - 允许转销售单。
   - 同一报价版本只能生成一张销售单，重复操作必须拦截。
   - 如果明细关联 `quote_candidate` 产品，在成功转销售单时转为 `formal`。

2. 暂无后续
   - 记录结果、操作人、时间和备注。
   - 报价单停留，不自动进入下一节点，也不自动关闭或删除。
   - 后续客户重新反馈时，销售仍可改为“接受价格”或“价格有问题”。

3. 价格有问题
   - 记录客户反馈和备注。
   - 从采购询价重新开始：生成或重开与该报价单关联的询价单。
   - 采购重新比价，老板重新确认售价。
   - 不新建另一条无关联报价业务链；更新同一报价单的版本号（V2、V3……），保留每个历史版本、价格和操作记录。
   - 新版本再次进入“待客户反馈”。

前后端必须校验合法状态迁移，不能只靠按钮隐藏。例如未老板确认、客户未接受或已转销售单时，API 都必须拒绝非法转单。

## 六、询价单供应商报价字段

以下字段属于“每一条供应商报价”，不是整张询价单共用字段，因为不同供应商的数据可能不同：

- 产品尺寸：文本，界面显示单位 `cm`，示例 `40×30×10`。
- 产品材质：文本。
- 产品包装：文本。
- 产品重量：数值，单位 `g`。
- 大货交期：文本，单位天，必须支持范围，示例 `7-10`。
- 装箱数：整数，单位“个”。
- 外箱尺寸：文本，界面显示单位 `cm`，示例 `55×45×40`。
- 外箱毛重：数值，单位 `kg`。
- 备注：多行文本；打样时间、打样费用等内容统一写在备注，不再建立独立打样字段。

实现要求：

- 在采购提交比价表单中，每个供应商报价录入块都显示以上字段。
- 在询价详情和老板确认区域中按供应商显示这些字段。
- 兼容历史询价数据；缺失字段显示“-”或“未填写”，不能导致页面或接口报错。
- 新字段默认允许为空；现有“至少两家供应商报价”、供应商和采购价等核心校验保持不变。
- 字段必须在 `runtime` 和 `prisma` 路径中完整保存、读取、更新和写入审计日志。
- 不新增“打样时间”和“打样费用”字段。

## 七、权限与数据可见性

- 采购、采购主管：录入和查看供应商询价、采购价及新增的比价字段。
- 老板、管理员：查看完整比价信息，老板可选择最终供应商并确认售价。
- 销售、销售主管：不能看到供应商名称、采购价和内部比价明细；可以看到老板确认后的最终销售价、报价版本和客户反馈状态。
- 客户反馈操作由销售/销售主管完成。
- 审计日志返回给销售角色时，继续脱敏采购价、供应商和其他内部采购字段，不能通过日志泄露。

## 八、页面与交互

- 更新销售中心对需求单和报价单用途的说明，不能继续显示“需求单只选产品库、报价单手填新品”的旧文案。
- 需求/报价详情页明确显示当前流程状态和下一步可执行动作。
- 老板审批需求单、老板确认报价售价、销售记录客户反馈必须是三个语义独立的操作区域。
- 报价单详情增加客户反馈区域，清楚显示：待反馈、客户已接受、暂无后续、价格有问题/重新询价中。
- 价格有问题后要显示当前报价版本和历史版本，避免销售误以为生成了另一张无关报价单。
- 延续项目现有页面风格，不做无关 UI 重构。

## 九、数据、状态和审计

- 为上述流程设计清晰、可读的状态，不复用语义不同的旧状态。
- 保持来源关系可追踪：需求单 → 询价单 → 报价单版本 → 销售单。
- 每次创建、提交、老板审批、老板定价、选择供应商、销售记录客户反馈、重新询价、报价升版、转销售单和产品转正式都要写审计日志。
- 操作应尽量幂等，避免重复询价单、重复报价版本、重复候选产品和重复销售单。
- Prisma 路径中需要跨记录更新时使用事务，避免只更新一半；runtime 路径保持同等结果。

## 十、测试与验收

至少补齐以下测试：

- 需求单可选择产品库产品，也可手填新产品。
- 报价单只能选择产品库产品，前端无手填入口，API 拒绝手填载荷。
- 产品库需求提交后必须老板审批，老板不修改售价；未审批不能转销售单。
- 手填新品需求提交后生成询价单，不能直接转销售单。
- 询价的每家供应商报价可保存并回显新增字段和备注。
- 老板确认新品售价后创建/复用 `quote_candidate` 产品，并转成报价单而不是销售单。
- 产品库报价单首次提交不生成询价单，老板确认售价后进入待客户反馈。
- 销售可记录三种客户反馈；其他无权限角色不能调用该操作。
- 客户接受后可转销售单，候选产品转 `formal`。
- 销售编码规则可独立配置，不能选择供应商编码段；候选产品转正式时自动生成唯一销售编码。
- 暂无后续不自动进入下一节点，后续仍可继续记录反馈。
- 价格有问题时从采购询价重走流程，老板重新定价后同一报价单升版并再次待客户反馈。
- 历史无新增字段的数据仍能正常读取。
- 销售接口和审计日志不泄露采购价、供应商及内部比价数据。
- runtime 与 prisma 两套测试都覆盖关键状态迁移。
