## 2. 分批修改清单

### 第 1 批：数据、人员归属和日志可信

#### M01：各页面的数字要一致

**修改状态：已验收。实施版本：v1.2.2。验收日期：2026-09-28。**

- 要改什么：同一账号、相同时间和范围下，工作台统计与列表使用一致的业务数据；清除业务列表混入的固定示例。明确统计的是“我的、团队还是全部”，并能核对组成数字的明细。
- 验收：不再出现相同口径下销售工作台 6 单、列表 9 单；数字能与明细逐条核对。
- 范围说明：列表混入示例已定位于 runtime 分支，不能据此认定生产 MySQL 也有同样问题；修改时分别核对两种存储模式。
- 实际修改：关闭 runtime 七类业务列表的自动示例拼接和空库询价示例写入，移除正式列表接口失败时的前端示例回退；保留已经持久化的记录。销售汇总与列表使用同一会话和负责人 ID 过滤；列表、工作台说明本人、团队或全部及时间范围。经营看板和管理报表沿用既有全量权限与统计，明确标为“全部”。
- 验证：空 runtime 列表无示例，已保存记录仍可见；Prisma 不混入 runtime。隔离 runtime 和独立 MariaDB/Prisma 实际接口核对新增员工的列表数量、销售汇总及待办；管理员页面核对销售工作台 6 单与列表 6 条。
- 边界：不凭单号或姓名删除历史记录；销售汇总仍为全部时间，应与无额外状态、日期筛选的列表核对。金额计入节点和毛利/月报公式仍按原规则，留待 M03/M04。

#### M02：待办必须是真实任务

**修改状态：已验收。实施版本：v1.2.2。验收日期：2026-09-28。**

- 要改什么：销售、采购、运营工作台接入真实待办，移除固定示例任务；与首页、待办中心使用相同的账号和业务范围。
- 验收：各入口数量一致；完成一项任务后，相应入口同步更新，不再保留示例待办。
- 实际修改：三个工作台复用正式待办 API，不再维护固定任务或按姓名二次过滤；首页、待办中心、侧栏使用相同签名身份、模块权限和数据范围。成功操作、刷新及切换入口重新校验侧栏数量。
- 验证：真实任务内容与单据链接回归；模块权限、个人/团队范围及处理后旧任务消失回归；两种存储模式实际提交、驳回后核对任务节点变化。
- 边界：沿用原岗位分组和业务节点。本批不实施 M11 的全量未完成查询、M12 的处理/跟进分组及 M13 的逾期排序。

#### M10：新员工的单据归属必须正确

**修改状态：已验收。实施版本：v1.2.2。验收日期：2026-09-28。**

- 要改什么：建单、指派负责人、本人数据范围都使用真实员工身份，不能把未识别的员工归到演示账号；姓名只用于显示。
- 验收：新增两名员工分别建单，归属互不混淆；改名后历史归属不变；停用员工不破坏历史记录，不能再被错误选为新单负责人。
- 实际修改：真实 userId 贯穿登录、签名会话、建单人、负责人选项、采购分配及本人数据过滤，中文姓名可正常传递。新选负责人须有效且在权限范围内；编辑保留当前历史/停用负责人选项，后端只允许保留原负责人。草稿编辑先验证原单据访问权限，避免借重新选负责人改写他人单据。单据操作日志使用当前操作人 ID。
- 验证：新增同名销售员工归属与可见范围互不混淆，伪造建单人被覆盖为实际登录用户；停用员工不能登录或成为新单负责人，历史归属不变。独立 Prisma 实际改名后原单据、汇总及待办仍可见；采购同名、分配改名及停用历史负责人编辑由回归测试覆盖。
- 历史处理：仅为已核实的原始种子账号 ID+username、且旧 ID 未分配给真实账号时提供只读兼容；不重写数据库或 JSON 历史负责人。无法证明归属的旧记录仍需人工核对，不根据显示姓名推断归属。

#### M14：单据日志只显示当前单据

**修改状态：已验收。实施版本：v1.2.2。验收日期：2026-09-28。**

- 要改什么：销售、采购、发货、售后详情只展示本单日志；全部业务日志留在日志中心。默认显示近期关键动作，详细差异可展开。
- 验收：销售单 #104 不出现 #105 的日志；能看清谁提交、谁驳回、改了什么。
- 实际修改：四类详情按业务类型和本单 ID 请求日志，并防御性过滤响应；日志中心保留授权的全模块记录。默认近期 8 条，其余可展开；字段差异可展开查看全部变化，包含产品行单价等嵌套字段。操作人名称来自用户目录，目录无名称时显示操作人 ID，避免把单据负责人误认成操作人。
- 验证：不同单据、同 ID 不同模块、runtime/Prisma 日志过滤和无审计权限回归；实际销售 #104 只展示本单 3 条日志，管理员驳回和员工提交可区分。覆盖超过 5 个字段变化及产品行数量不变但单价变化。

#### M15：加载失败不能显示为 0

**修改状态：已验收。实施版本：v1.2.2。验收日期：2026-09-28。**

- 要改什么：区分“加载中、确实为零、加载失败”；失败时显示暂不可用及重试入口，不能同时提示“暂无待办”。更新时间对应当前区块实际取得的数据。
- 验收：接口失败时，不会让用户误以为没有订单、任务或利润；恢复后能重新取得真实数据。
- 实际修改：首页、待办中心、三类工作台、七类业务列表、经营看板、报表及侧栏分别处理加载中、成功零值和失败；失败区块显示“暂不可用”和重试按钮，成功区块继续显示。更新时间取各区块实际响应，不以另一接口的时间代替。
- 页面加载修订：根据用户反馈，将账号、侧栏与页签保留在正式布局层；切页等待数据时只在右侧内容区域显示加载提示，避免整页短暂替换。内容返回后再登记正确页签标题；未登录的登录页保持独立。
- 验证：网络失败、非成功响应、无效数据、部分区块成功及七类列表真实空库等回归；实际页面在开发 API 重启和隔离代理返回 503 时显示失败提示、不冒充 0、“暂无待办”或示例单据。恢复接口后点击重试，销售列表恢复为本人的 1 条记录，侧栏恢复 1 项待办。

### 第 2 批：销售金额、收款和操作原因准确

#### M03：销售金额按业务状态统计

**修改状态：已修改待验收。实施版本：v1.2.2。业务口径：已于 2026-09-28 确认。**

- 要改什么：提交审核后计入提交金额，主管驳回后扣除，重新提交按新金额计入；采购单发货后计入已发货金额；原售后待闭环卡片改成作废金额。
- 详细规则：沿用第 3 节 R01～R03；2026-09-28 用户确认采购实际发货数量按销售价计入，作废销售单整单金额计入作废并从提交金额扣除。
- 验收：草稿、提交、驳回、重提的金额变化准确；发货和作废按确认后的口径核对；刷新或重复操作不重复累计。
- 实际修改：销售汇总按已提交的审批/执行状态计算提交金额，草稿、驳回、作废不计入；已发货金额逐条读取实际采购发货批次，按来源销售行售价 × 本批实际数量计算，不使用累计数量或整单金额。运输状态推进不重复增加；作废销售单整单金额单独展示，替换原售后待闭环卡片。沿用同账号、全部时间及原数据范围。
- 数据异常：本账号可见批次缺少明细、无法对应来源销售行或售价/数量无效时，汇总返回明确错误，工作台提示暂不可用及重试，不以 0 掩盖。其他账号的异常批次不影响本人汇总。
- 验证：runtime/Prisma 金额回归覆盖提交、驳回、修改重提、审批、作废、多产品多批次部分发货、运输状态变化、不同账号及异常明细；实际两模式业务流程取得提交 223.50、发货 24.70、作废 223.50 元，符合两张 223.50 元销售单中一张作废、另一张只发 2 件 × 12.35 元的结果。浏览器核对现有 6 单、提交 52.5 元及新卡片/口径。

#### M05：收款不能一键变成全款到账

**修改状态：修改中。实施版本：v1.2.2。业务口径：本批仅管理明确选择的收款状态（2026-09-28 用户确认）。**

- 要改什么：分开“登记收款”和“财务复核”。登记前让用户明确选择真实收款状态并看到结果；财务确认不能自动把未付款改成已全款。
- 原待确认：仅管理状态或同时记录逐笔金额和凭证。2026-09-28 用户确认本批只管理明确选择的收款状态；逐笔实收、累计、剩余和凭证不在本批范围。
- 验收：普通确认不会把未收款或定金变成全款；用户能知道此次操作到底登记了什么。
- 实际修改：登记表单默认为“请选择”，须选择未收款、定金、全款或预付款抵扣；成功提示显示实际登记结果。财务复核只读取已保存的收款状态，不接受请求中伪造的全款状态，未收款不能复核。两种模式保存真实操作人和前后变化，缺失或无权访问的单据不报成功。并发更新不覆盖已取得的新状态，冲突提示刷新。
- 验证：非法状态、未收款伪造全款复核、定金复核后保持定金、无权限/个人范围、真实操作人、JSON 原始快照冲突、日志失败回滚和履约同步竞争均有回归。真实 Prisma 并发测试通过，runtime/Prisma 实际签名接口验证定金与复核独立，实际页面默认不选择，空白提交不能登记。
- 剩余（故保留“修改中”）：原页面在采购中及内部 closed 后隐藏收款/复核入口，本批暂保留；是否放开已审批单据的这两个节点，已向用户提问。收款状态变化后是否重置财务待复核，也已向用户提问；答复前保留原复核状态，不改其业务含义。逐笔金额和凭证已明确不在本批范围。

#### M08：作废、驳回、异常填写真实原因

**修改状态：已修改待验收。实施版本：v1.2.2。**

- 要改什么：用简短表单填写实际原因，不再暗中写入“客户取消订单”“货物破损”等固定内容。驳回后能看到修改要求；作废前说明受影响的关联单据。
- 验收：物流延误不会登记成破损；主管的驳回理由能被销售看到；正常审批通过仍可简洁完成。
- 实际修改：销售/采购/售后驳回和发货异常提供空白必填原因，销售作废前展示实际关联未发货采购单号与影响；服务器重新核对关联和实际发货，不相信隐藏的“未发货”字段或客户端采购 ID 列表。已登记发货后不能作废。当前单据展示真实修改要求、作废/异常原因，日志保留操作人、时间和前后变化。
- 权限与失败保护：本批采购驳回/作废、售后驳回、发货异常按详情相同的数据范围校验；不存在、越权、空白/非文字原因、过时状态均不写业务或日志。销售作废与发货竞争须由共同状态校验及 Prisma 销售源行锁协调。

- 验证：两模式真实原因落库和显示，签名 HTTP 的岗位/模块/动作/个人范围，缺失单据、空白/非文字原因及过时状态；真实 Prisma 和 runtime 作废/发货竞争只能一项成功。runtime 异步权限检查后重新读取状态，标到货与标异常竞争不能用旧状态覆盖到货。实际页面空白驳回被拦截，采购/售后/异常写入由隔离真实接口流程核对。
