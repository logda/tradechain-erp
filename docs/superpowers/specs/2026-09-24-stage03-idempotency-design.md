# 第 03 段全系统写入防重复设计

## 背景与范围

需求 R19-01～R19-05：保存、提交、审批、转单、发货和待办处理等数据写入操作，在页面请求中立即锁定；成功后旧操作不重新开放；失败后可重试。同一动作重复到达 API 时不能重复建单或重复推进。保留历史数据与现有页面风格，runtime 和 Prisma 两种存储都要成立。

## 决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| Q1 | 每次用户提交意图生成稳定的幂等标识，由 Web Server Action 传递给 API；失败重试沿用同一标识，用户更改内容后产生新标识。 | 双击、重放与网络响应丢失时都可识别为同一意图；不凭业务字段推断“相同单据”。 |
| Q2 | API 全局写入拦截器只对带标识的业务写入做持久化去重；标识按当前已认证操作者隔离，绑定方法、URL 与请求体摘要。 | 不改业务 DTO，也避免同一标识被换内容或换接口复用。未带标识的旧 API 调用维持兼容，原有业务状态校验仍执行。 |
| Q3 | runtime 使用独立 JSON 记录，Prisma 新增幂等记录表及迁移；同一标识已成功时返回原结果，处理中时拒绝新执行，失败时可重试。 | 两种模式都跨进程重启保留成功结果；数据库唯一约束处理并发抢占。 |
| Q4 | 同一单据的不同状态动作须串行，并由业务状态校验决定是否允许推进；修补发现的状态校验缺口。 | 不同标识也不能把同一节点推进两次。待办从业务状态派生，不单独维护“已处理”标志。 |
| Q5 | 成功后按钮保持禁用直至刷新状态或导航完成；保存类表单在用户实际改动后允许下一次保存。 | 旧视图不能再次执行；又不阻止真实的后续编辑。 |

## 实施和验证边界

先覆盖共用 `MutationActionForm` 及正式业务的新建、保存、提交、审批、转单、发货表单，再逐项核对写入入口。API 同标识的同时请求、响应丢失后的重复请求、失败重试、不同操作者/请求体冲突、runtime/Prisma 持久化均需测试。Prisma 用增量迁移，不能清库。若 API 在业务写入完成后、幂等结果写入前异常退出，记录保持处理中并拒绝自动重放，避免重复建单；该罕见场景由运维核查原单据后处理，不能静默重新执行。
